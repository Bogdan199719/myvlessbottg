# Technical Audit And Backlog

Этот файл содержит только актуальные, подтверждённые ограничения и направления
улучшения. Он не является журналом выполненных задач или снимков production:
история изменений хранится в Git. Не добавляйте сюда меняющиеся количества
пользователей, ключей, транзакций и хостов, разовые результаты запуска или
данные конкретных пользователей.

Последняя сверка с кодом: 2026-10-03.

## Текущее состояние

- SQLite работает в WAL-режиме; `PRAGMA quick_check` на production-БД проходит.
- Критические платёжные операции и durable checkpoints выполняются атомарно.
- Состояние подписки в SQLite является источником истины для DB→3x-ui reconcile.
- Обратная panel→DB синхронизация управляется отдельной настройкой
  `panel_sync_enabled` и по умолчанию выключена.
- XTLS-синхронизация управляется `xtls_sync_enabled`, выполняет блокирующие
  запросы вне общего asyncio event loop и по умолчанию выключена.
- Ручное обслуживание параллелит только независимые физические панели;
  logical hosts одной панели обрабатываются последовательно.
- Записи 3x-ui на одну физическую панель сериализованы между scheduler,
  платежной выдачей, административными операциями и XTLS.
- Восстановление платежей запускается отдельно от обслуживания панелей.
- Повторный запуск ручных maintenance и массовых административных операций
  блокируется внутри процесса.
- Для hot lookup ключей по хосту используется индекс `vpn_keys(host_name)`.

## Актуальный технический backlog

### Scheduler и пакетные операции SQLite

Основной reconcile и panel→DB sync проходят logical hosts последовательно.
Безопасное ускорение — ограниченный параллелизм только между физическими
панелями после внедрения общей блокировки. Panel→DB sync также выполняет ряд
отдельных SQLite connection/commit для каждого ключа; изменения следует сначала
рассчитать из одного panel snapshot, затем сохранить одной транзакцией на хост.
Правила выбора срока и источник истины при этом менять нельзя.

### Разделение оставшихся периодических задач

Maintenance и уведомления по-прежнему идут в одном последовательном цикле.
Медленная панель может задержать уведомления, но уже не задерживает проверку
и повторную выдачу подтверждённых платежей. Дальнейшее разделение требует
сохранить порядок бизнес-операций и защиту от повторного запуска.

### Миграции и старые backfill

Инициализация БД использует набор idempotent-проверок вместо таблицы версий
схемы. Некоторые исторические backfill повторно обходят данные при старте.
Долгосрочное улучшение — версионированные миграции с отдельной проверкой на
копии production-схемы. Включать SQLite foreign keys отдельным PRAGMA без аудита
существующих связей и миграции схемы нельзя.

### Наблюдаемость выдачи

Текущие durable metadata/checkpoints защищают повторную обработку оплаты и
сохраняют абсолютную дату окончания. Отдельный per-payment/per-host fulfillment
ledger остаётся полезным для диагностики частичных выдач и истории retry, но
это расширение модели данных, а не обязательное исправление текущей логики.

### Границы раннего восстановления платежей

Восстановление до сохранения абсолютного срока ограничено новыми заказами
YooKassa при запуске после остановки предыдущего процесса. Исторические заказы
без маркера безопасного протокола нельзя автоматически пересчитывать: срок мог
быть потерян после уже выполненного изменения панели. Запись платежа, этапов и
финансовый учёт уже защищены ID отдельной попытки. Для восстановления зависших
ранних операций текущего процесса остаётся обеспечить безопасное завершение
старого обработчика и внешних команд: проверка владельца сама по себе не
отменяет отправленную команду панели. Для новых заказов CryptoBot подтверждение
проверки суммы уже сохраняется до выдачи; раннее восстановление этого провайдера
пока не включено. Для Stars нужно отдельно проверить полноту сохранённых сведений
об оплате перед расширением раннего восстановления, для P2P — безопасная очередь повторной
выдачи. Эти расширения не следует включать простым снятием проверки срока.

### Принадлежность внешнего счёта CryptoBot заказу

Внешний ID счёта не сохраняется вместе с локальным заказом при создании счёта.
Подписанное уведомление связывается с заказом по `tx_id` из payload. Следующее
усиление — сохранять внешний ID и проверять его соответствие заказу и провайдеру.
Это требует отдельной проверки старых счетов без такого ID; ошибочный резерв
заказа другого способа оплаты также должен отклоняться до изменения записи.
