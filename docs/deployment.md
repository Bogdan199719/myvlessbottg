# Deployment

После установки версии с привязкой административной сессии к логину и хешу
пароля потребуется повторный вход в веб-панель. Это не меняет учётные данные
и не отзывает VPN-подписки. Кодовый откат выполняется без замены рабочей базы
старой копией: новые продажи и продления должны сохраняться. Проверка
`ISOLATED_ADMIN_TEST=1 python scripts/check_admin_reporting_sessions.py`
предназначена исключительно для контейнера без сети и с синтетической базой;
на production-процессе её запускать нельзя.

## Требования

- Docker Engine с Docker Compose;
- образ приложения использует Python 3.12 на Debian 13;
- домен с A/AAAA-записью на сервер;
- открытые снаружи порты `80` и `443`;
- токен Telegram-бота, Telegram ID администратора и учётные данные 3x-ui.

Контейнер намеренно слушает только `127.0.0.1:1488`. Не открывайте этот порт во внешний интернет: используйте HTTPS reverse proxy.

Одну рабочую SQLite-базу обслуживает один процесс приложения. При замене контейнера предыдущий процесс должен полностью остановиться до запуска следующего: раннее восстановление платежей и сброс пользовательских флагов выполняются до запуска обработчиков. Параллельный запуск нескольких экземпляров с общей БД требует отдельной защиты владения операциями.

## Запуск

```bash
git clone https://github.com/Bogdan199719/myvlessbottg.git
cd myvlessbottg
cp .env.example .env
chmod 600 .env
docker compose up -d --build
docker compose logs -f bot
```

До запуска заполните в `.env` минимум `TELEGRAM_BOT_TOKEN`, `ADMIN_TELEGRAM_ID`, `DOMAIN`, `FLASK_SECRET_KEY`, `PANEL_LOGIN` и `PANEL_PASSWORD`. Для `FLASK_SECRET_KEY` используйте случайное значение длиной не менее 32 символов, например `openssl rand -hex 32`.

Проверка локального сервиса:

```bash
curl -fsS http://127.0.0.1:1488/healthz
```

На первом старте приложение создаёт или мигрирует `users.db` и переносит стартовые настройки из `.env` в SQLite. После этого рабочие параметры хранятся в `bot_settings` и меняются через админку.

## Reverse proxy и HTTPS

Установите Nginx и Certbot, создайте `/etc/nginx/sites-available/myvlessbot`:

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name vpn.example.com;

    # Токены подписок и legacy webhook secrets находятся в URL.
    # Не записывайте эти пути в access log.
    location ~ ^/(?:sub|happ|incy|cryptobot-webhook)/ {
        access_log off;
        proxy_pass http://127.0.0.1:1488;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        proxy_pass http://127.0.0.1:1488;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # Массовые действия в админке ожидают ответы нескольких 3x-ui панелей.
        proxy_connect_timeout 5s;
        proxy_send_timeout 60s;
        proxy_read_timeout 300s;
    }
}
```

Замените `vpn.example.com` на значение `DOMAIN`, включите конфигурацию и получите сертификат:

```bash
sudo ln -s /etc/nginx/sites-available/myvlessbot /etc/nginx/sites-enabled/myvlessbot
sudo nginx -t
sudo systemctl reload nginx
sudo certbot --nginx -d vpn.example.com --redirect
```

Проверьте `https://vpn.example.com/healthz`, затем войдите в админку по `https://vpn.example.com/login` с `PANEL_LOGIN` и `PANEL_PASSWORD`. Если перед Nginx есть CDN или другой proxy, добавьте его непосредственный CIDR в `TRUSTED_PROXY_CIDRS`; не доверяйте произвольному `X-Forwarded-For`.

После настройки Certbot убедитесь, что HTTPS- и HTTP-серверы сохраняют отдельный `location` с `access_log off` для `/sub/`, `/happ/`, `/incy/` и `/cryptobot-webhook/`. Если HTTP перенаправляется на HTTPS, размещайте `return 301` внутри `location /`: директива `return` на уровне `server` выполняется до выбора location и снова раскроет секретный URI в общем access log.

Альтернатива: `bash install.sh` автоматизирует установку Docker, Nginx и Let's Encrypt на Ubuntu/Debian. Запускайте его только на сервере, где домен уже резолвится на этот хост.

## Состояние, backup и restore

- `.env`, `users.db` и backup-файлы — runtime-данные, а не исходный код;
- храните `.env` с правами `600`;
- backup/import из админки включает `.env` только при явном выборе в форме;
- restore сначала сохраняется как pending, а перед стартом Flask, ботов и scheduler применяется с rollback-копиями БД и `.env`.

На этом сервере cron (`/etc/cron.d/backup_my_project`, шаблон
`scripts/backup_project.cron`) запускает `scripts/backup_project.sh` ежедневно
в 05:00 МСК.
Архивы находятся в `/bacupmyproject/`; после успешной проверки нового архива
остаются три последние завершённые копии. Архив включает файлы проекта и `.env`.
Рабочая `users.db` попадает в `backup_extra/sqlite/users.db` как согласованный
SQLite-снимок; рядом сохраняется SQL-дамп этого же снимка. Живые файлы
`users.db`, `users.db-wal` и `users.db-shm` повторно не архивируются.
Скрипт проверяет SQLite, gzip, состав архива и создаёт SHA-256; при ошибке
сохраняет предыдущие завершённые копии. Проверка без production-БД:
`python3 scripts/check_backup_project.py`. Ручной запуск на сервере:
`TZ=Europe/Moscow bash scripts/backup_project.sh`; результат смотрите в
`/var/log/backup_my_project.log`. Этот cron хранит копии только на данном сервере.

## Обновление

Не меняйте файлы работающего приложения через `git pull`, `git reset` или pip.
Сначала сохраните текущие незакоммиченные изменения и создайте отдельную копию
исходников. Подготовьте backup данных и конфигурации, проверьте SHA-256 и SQLite,
сохраните предыдущий образ и конфигурацию запуска.

Соберите и проверьте новый образ до остановки production. Исходники и скрипты
рабочей версии закрепляются отдельными read-only томами; runtime-каталог с
актуальной SQLite и `.env` сохраняется. Обычный `restart` не заменяет код такого
тома новым содержимым образа. Обновление выполняется контролируемой заменой:
остановить прежний процесс, дождаться его завершения, затем запустить новый образ
с томами этой версии. Два экземпляра с общей базой или Telegram-токеном одновременно
запускать нельзя. Блокировка запуска защищает общие каталог проекта и путь базы.

`ENABLE_WEB_UPDATES` сохранён для совместимости `.env`. Проверка наличия обновлений
остаётся доступной, но `perform_update` не выполняет git/pip и не перезапускает
процесс даже при включённом флаге. Миграции, зависимости и способ отката нужно
проверять до выкладки; изменение зависимостей не должно происходить незаметно
внутри работающего приложения.

После запуска проверьте `/healthz`, оба бота, завершение фоновых проходов,
подключение к панелям и чтение существующей подписки. Не создавайте реальные
платежи и не продлевайте доступы ради проверки. Не публикуйте URL подписок и
конфигурации. При неисправности верните прежний совместимый образ и его тома кода,
сохранив текущую базу с новыми платежами. Восстановление старой базы поверх новых
продаж не является обычным откатом приложения.

## Направления синхронизации 3x-ui

Основная сверка состояния клиентов из БД в панели выполняется отдельно от обратной синхронизации: она сохраняет сроки и ограничения согласно данным бота. Успешное сообщение `DB enforce finished` не означает, что сохранённые ссылки обновлены из панели.

`panel_sync_enabled` управляет обратной сверкой с панелями и по умолчанию выключен. Этот режим обновляет параметры ссылок и учитывает серверные сроки, а отсутствующие клиенты помечает для повторной проверки. Снимок inbound загружается через общий слой совместимости API, сохраняющий настройки транспорта, в том числе XHTTP. Изменение параметров ссылки, например `flow`, требует обновления даже при неизменном сроке доступа.

`xtls_sync_enabled` отдельно управляет исправлением XTLS-параметров клиентов в панелях и также по умолчанию выключен. Не включайте оба режима только для исправления одной устаревшей ссылки: сначала сравните её с клиентом панели, сохраните исходную запись и проверьте точечное исправление. Пользователь должен обновить подписку в приложении, чтобы получить новую конфигурацию.

Регрессионные проверки этих путей: `scripts/check_scheduler_integrations.py` и `scripts/check_xui_connection_equivalence.py`. Эти флаги хранятся в `bot_settings`; перезапуск сам по себе не включает их.

## Проверки перед деплоем

Все изменяющие состояние проверки выполняйте в отдельной копии исходников,
без production `.env` и баз. Используйте готовый образ с теми же зависимостями,
Docker `--network none`, read-only подключение исходников и временную writable
копию проекта в `/tmp`. Для проверок аналитики и согласованности создайте только
синтетическую SQLite; не подключайте рабочую базу к тестовому контейнеру.

Запускайте применимые `scripts/check_*.py` в таком окружении. Проверка
`check_xui_real_panel_isolated.py` дополнительно требует отдельную тестовую панель
и явный `ISOLATED_PANEL_TEST=1`; нельзя заменять её рабочей панелью. Перед
выкладкой также нужны проверка синтаксиса Python, `bash -n install.sh`,
`docker compose config --quiet` и `git diff --check`. Успех тестов не заменяет
наблюдение за реальным сервисом после выкладки.

`check_subscription_consistency.py` читает live-БД и проверяет, что каждый active trial и active paid global пользователь имеет ключ на каждом включённом XUI-хосте. По умолчанию скрипт маскирует идентификаторы; `--show-identities` предназначен только для доверенной локальной диагностики.

`check_subscription_notifications.py` проверяет на отдельной синтетической БД и имитации Telegram цепочки paid/trial/free/MTG, группировку по серверам, защиту от дублей, новый цикл после изменения срока, повтор после ошибки отправки и тексты onboarding при включённом и выключенном trial.

`check_subscription_business_rules.py` и `check_profit_accounting.py` используют временную SQLite и не изменяют production-данные.

Для изменений оплаты и trial дополнительно проверяются:

- `check_payment_reservation_checkpoints.py` — сохранение актуальных checkpoints при повторном резервировании, конкурирующие обработчики и однократный финансовый учёт на временной БД;
- `check_payment_attempt_ownership.py` — смена владельца попытки, отказ устаревшим записям и финализации, конкурентное однократное начисление и освобождение только собственного пользовательского флага;
- `check_paid_provider_retry_checkpoints.py` — настоящий фоновый повтор Stars/CryptoBot на временной БД и имитации XUI/Telegram: устаревший снимок очереди, свежий срок и начисления, сохранение текущих столбцов оплаты, повреждённая metadata и изменившийся статус;
- `check_cryptobot_payment_confirmation.py` — проверка подтверждения CryptoBot на временной БД: некорректная сумма, сохранение подтверждения до выдачи, безопасный повтор и совместимость старых заказов;
- `check_yookassa_webhook_retry.py` — настоящий Flask webhook и выдача на имитации Telegram, YooKassa и XUI: частичный сбой, повтор, недоступный бот, прерывание до сохранения цели с восстановлением после смены процесса и отклонение некорректных уведомлений;
- `check_early_payment_recovery.py` — восстановление новых ранних заказов YooKassa, исключение старых и неоднозначных состояний, сохранение новых checkpoints при конкурирующем изменении записи;
- `check_trial_delivery_safety.py` — ошибки Telegram до выдачи trial, конкурирующие нажатия и сохранение захвата после изменения панели.

`check_yookassa_webhook_retry.py` также проверяет устаревшие финализаторы исключений YooKassa/CryptoBot, запоздалый ответ XUI после смены попытки и передачу ID попытки в обработчиках Stars/P2P. Защита попыток хранится в metadata и не требует новой колонки или изменения тарифов.

Перед выкладкой запускайте эти проверки в отдельной копии исходников без production `.env`, с тестовой БД и отключённой сетью. Проверки не создают реальные платежи и доступы. После выкладки отдельно проверьте здоровье приложения, получение сохранённых подписок и завершение фоновых задач. При возврате предыдущего кода не заменяйте live-БД старым backup: новые платежи и пользователи должны сохраниться.

`check_payment_analytics.py` читает рабочую БД в режиме read-only и получает
согласованный снимок через SQLite Backup API, включая уже закоммиченные данные
из WAL. Миграции и проверки аналитики выполняются только на временном снимке.

`python3 scripts/check_subscription_issuance_speed.py` проверяет выдачу после оплаты
и через админку на имитации панелей: ограничение параллелизма, порядок внутри
панели, отмену, сохранение блокировки работающего HTTP worker, единый срок,
частичные ошибки и обязательное сохранение ключей в БД. Сравнение времени в этом
скрипте использует искусственные сетевые задержки. Для оценки реальной выдачи
после обновления смотрите длительность `XUI subscription batch` в журнале сервиса;
прохождение теста само по себе не подтверждает работу продакшена.


Для проверки совместимости клиентского API используйте `scripts/check_xui_client_write_safety.py` и `scripts/check_xui_canonical_preservation.py`. Дополнительная проверка `check_xui_real_panel_isolated.py` требует отдельного контейнера с отключённой внешней сетью, синтетической БД 3x-ui и явно заданным ISOLATED_PANEL_TEST=1; её нельзя запускать против рабочей панели. Проверки выдачи/продления и trial выполняются на тестовых данных, без реальных платежей.

При узком обновлении интеграции сначала сохраните согласованные SQLite snapshots, исходники и образ. Откат кода не должен восстанавливать старую БД поверх новых продаж. После загрузки проверяйте canonical read-back и несколько проходов scheduler, различая core hot apply, реальный restart Xray и restart самой панели. Отсутствие новых restart за ограниченное окно не доказывает отсутствие всех будущих причин.

Проверка `python3 scripts/check_subscription_operation_safety.py` воспроизводит
конфликт trial/manual/auto-provision на синтетической SQLite, сохранение UUID и
ссылки, обычное продление, намеренное сокращение, очередь одного пользователя,
ошибки и отмену запроса, устаревшие снимки фоновых задач. Она не вызывает API и
не открывает рабочую базу. Истёкшее ожидание записи не освобождает резервацию до
завершения уже запущенного HTTP worker; фактический срок ожидания ограничивается
также сетевыми таймаутами worker.

Координатор действует внутри одного процесса совмещённого bot/admin service.
При переходе к нескольким процессам/репликам требуется межпроцессная резервация;
масштабировать этот сервис только увеличением числа workers нельзя. При адресном
восстановлении срока используйте сравнение с ожидаемым текущим состоянием и
проверку API/DB, не повторную выдачу всего тарифа. Откат кода не заменяет свежие
данные продаж старой копией базы.

Диагностика `/healthz` сама не перезапускает приложение. После обновления
проверяйте `runtime.tasks`, `runtime.cycles`, `runtime.bots` и `runtime.warnings`:
предупреждение о долгом этапе или ошибке API требует наблюдения, а не безусловного
рестарта. Намеренно выключенный бот не является аварией. Проверки
`check_stage1_runtime_health.py`, `check_stage1_mtg_logs.py`,
`check_stage1_cryptobot_invoice.py` и `check_stage1_login_bounds.py` воспроизводят
регрессии диагностики, журналов, рублёвого счёта и ограничения памяти авторизации
на искусственных данных. Запускайте их в изоляции вместе с платёжными и
подписочными проверками. Для возврата этих изменений достаточно прежнего кода;
миграций и восстановления старой базы не требуется.

Проверки `check_backup_paths_and_updates.py` и `check_full_backup_restore.py`
проверяют нестандартный путь SQLite, неисполнение `.env`, ротацию только архивов
с совпадающими контрольными суммами и полноценную цепочку восстановления на
синтетических данных. Вторая проверка требует контейнер с `--network none`:
она восстанавливает исходники, `.env` и согласованный снимок SQLite, проверяет
страховочную копию прежнего состояния и запускает только тестовый экземпляр.
Её нельзя направлять на production-базу или использовать вместо проверки наличия
внешней копии. При отсутствии адреса и ключей внешнего хранилища данные не
отправляются наружу.

Архив и его SHA-256 публикуются до ротации; завершённая пара синхронизируется
на диск, затем атомарно обновляется receipt последнего успеха. При отказе
публикации прошлый receipt и известные хорошие архивы сохраняются. Повреждённые
или незавершённые архивы автоматически не удаляются и не считаются хорошими
копиями при ротации; их необходимо отдельно проверить оператору.
